# 实现说明

## 任务执行

FastAPI 接收病例和问题，任务交给单工作线程执行。模型后端也持有锁，避免多个推理任务同时占用 GPU。LangGraph 串联事实抽取、观察、计划、工具、检索、临床证据对照、诊断和复核节点。影像 Agent 使用 NV-Reason，临床 Agent 使用 Lingshu，独立审查 Agent 使用 Qwen3-VL；协调修订使用 Lingshu。每个模型拥有独立处理器、生成状态和调用记录。复核发现问题时最多修订一次，仍未解决的问题随报告保存。

病例更新不会覆盖已有报告。每次任务保存当时的病史和问题，前端可以提示报告对应的资料与当前病例不同。服务重启会将未完成的任务标记为中断。

## 证据

病史原文、模型观察、工具输出和医学资料使用独立的证据编号。报告引用这些编号，前端点击编号可以定位到来源。事实抽取及临床证据对照中的原文片段会与来源文本核对，不能把中间候选诊断写成新增病史。

工具异常保留为失败证据。分类输出不是患病概率，解剖分割也不提供病灶定位。对胸片的模型观察可能有错，诊断和复核阶段默认同时接收原始胸片。

## 检索

参考资料数量较少，采用字符 TF-IDF 检索，便于处理中文与英文混合的病例和疾病名称。查询结合病史、计划中的候选疾病和影像观察。记录保留来源 URL 及摘要类型。

目前没有向量库、重排器或完整指南库。检索不到相关资料时，系统不能给检查建议补上虚假的知识引用。

## 输出与复核

本地模型使用 JSON Schema 解码约束，随后由 Pydantic 校验。语法修复只处理结构问题，不补造患者值；截断的完整报告不能用其中一个内层候选对象替代。

复核包含引用有效性、事实冲突、同义诊断重复和部分检查建议约束。`needs_review` 也可能由模型复核或临床证据对照未完成引起，不能直接当作诊断错误数。所有检查通过仍不等于医学正确。

## 多模型协作

影像 Agent 只接收原图和观察任务，不接收病史或临床 Agent 的诊断。临床 Agent 接收原始病例、原图、工具和检索证据；审查 Agent 接收待检查的报告及原始证据。审查的每个质疑必须同时能定位到报告原文与证据原文，无法匹配的质疑只保存为复核备注，不能直接改写诊断。

协调步骤最多修订一次，然后再次交给独立审查模型。仍未解决的问题保留在报告中，不进行多数投票。没有有效质疑时保存报告及最终处理状态。

只有主模型和一个辅助模型可以同时常驻 GPU。辅助槽在切换 NV 与 Qwen 前释放前一个模型及其分词器缓存；所有调用串行执行。切换加载耗时计入任务延迟。

报告的 `collaboration` 字段保存角色、实际模型、量化方式、来源版本、消息、质疑和修订。Agent 输出属于模型意见，未经临床验证。

## 生成循环

诊断名称限制为120字符，每条依据限制为400字符，引用保存在独立的 `evidence_ids` 列表。名称中出现方括号引用时，输出校验会拒绝该结果，不能通过裁剪来伪造完整报告。

生成时检测长段连续重复 token；触发后保留原始输出和停止标记，并从原始证据重新尝试一次。重试不附加重复的半成品，也不从内层对象补造报告。名称使用原生长度约束，避免大范围正则在解码时影响中文与速度；各模型的正则缓存独立初始化。

原失败病例的工程回归记录见 `evals/generation-regression.json`。回归结果不替换已经冻结的独立评测成绩。
